Read this first — four things in the V1.0 spec sheet contradict the firmware. The diagrams and tables below follow vital_monitor.ino, which is the working truth. The spec document needs correcting, not the code.
  1. Breathing rate is not measured from the PPG waveform. The spec says it is. The firmware computes BPM/4 + (98 − SpO2) × 0.5, clamped to 8–40. It is an arithmetic guess, not a measurement.
  2. The OLED and MAX30102 do not share an I²C bus. The spec says "Shared SDA, SCL". The code runs two separate buses: hardware I²C on GPIO6/7 and a bit-banged U8g2 bus on GPIO8/9.
  3. A 3.3 V LDO alone cannot power this device. The PMS5003 fan and laser need 5 V. A 3.7 V cell must go through a boost converter. The spec's BOM has no boost stage.
  4. The part is a MAX30105, not a MAX30102. The code calls setPulseAmplitudeGreen(), which only exists on the MAX30105 (it has a third, green LED). The library is shared, the silicon is not. Either part works if you drop that one line — but the BOM must say which you actually bought.

PMS5003 pins 3 (SET), 6 (RESET), 7 and 8 are left open. Both idle high internally, which is the run state.

Three wiring traps that will cost you an evening if you miss them.
  • GPIO9 is the boot strap pin on the ESP32-C3. If it is held low when the board resets, the chip enters USB download mode instead of running your sketch. It is used here as the OLED clock. Keep a 4.7 kΩ pull-up to 3V3 on it, and do not hot-plug the OLED.
  • GPIO20/21 are the UART0 pins. If the Arduino IDE is set to "USB CDC On Boot: Disabled", Serial takes those pins and fights the PMS5003. Set it to Enabled so the serial monitor runs over native USB instead.
  • PMS5003 logic is 3.3 V, supply is 5 V. Its TX output is 3.3 V, so no level shifter is needed — but its VCC pin must see 5 V or the fan will not spin and you will get silence on the UART.

1 · First light — sensors on a breadboard partial

Date: ____________

  • MAX30105 brought up on hardware I²C (GPIO6/7). Device ACKed at 0x57 on first try.
  • SSD1306 refused to appear on the same bus. Rather than debug address/timing conflicts, the OLED was moved to a second, software-bit-banged bus on GPIO8/9 using U8g2's SW_I2C constructor.
  • Consequence carried forward: this is why the spec sheet's "shared SDA/SCL" line is wrong, and why GPIO9 — a boot strap pin — ended up carrying a clock signal.

2 · PMS5003 silent on UART failure → fixed

Date: ____________

  • No frames returned. Two causes, both real:
  • Supply. The sensor was fed 3.3 V. Its fan did not spin. Moved to a 5 V boost output.
  • Pin contention. GPIO20/21 are UART0. With USB CDC disabled, Serial owned them. Switched the board setting to USB CDC On Boot: Enabled so debug output goes over native USB.
  • Switched the driver to pms.passiveMode() with an explicit requestRead() every 5 s, plus a 2.5 s timeout that clears pmsWaiting so a lost frame cannot deadlock the loop.

3 · Heart-rate reading jumping 40–180 bpm failure → fixed

Date: ____________

  • The Maxim reference algorithm alone was unusable on a loosely held finger.
  • Added an independent BPM path: 3-sample smoothing, 21-sample moving-average baseline removal, then peak counting with the threshold at 62 % of AC amplitude and a minimum peak spacing derived from a 160 bpm ceiling. Requires ≥ 3 peaks before reporting.
  • Added a window quality gate (windowIsClean): reject if IR saturates above 220 000, if AC swing is under 500 counts (finger too light), or over 8 000 counts (motion).

4 · Finger detection false-triggering on ambient light failure → fixed

Date: ____________

  • A fixed IR threshold worked at a desk and failed near a window.
  • Replaced with an adaptive baseline: whenever IR < 10 000, the no-finger baseline is updated with a 7:1 exponential average. Finger presence now means IR > baseline + 8 000.
  • Added a 3 s settling delay (SETTLE_MS) after finger-on before any value is published.

5 · Median filter sticking on a stale value failure → fixed

Date: ____________

  • A 6-deep median rejects outliers well, but when the real heart rate genuinely changed, the filter kept suppressing the new value as an outlier.
  • Added a 3-strike re-sync: if three consecutive readings disagree with the median by > 20 bpm (> 4 % for SpO₂) but agree with each other within 10 bpm (2 %), the history is flushed and the filter re-locks on the new level.

6 · BLE history transfer truncating failure → fixed

Date: ____________

  • History was first paged 8 records at a time. A GATT characteristic value is capped at 512 bytes and a record grew to ~75 bytes of JSON once timestamps became 10-digit Unix seconds — 8 records overflowed. Page size reduced to 5 (~400 bytes).
  • The original reader loaded up to 64 lines into a String array, which both capped history and risked heap fragmentation. Rewrote HistorySync to seek backward through /history.csv one line at a time, so RAM use is O(1) regardless of file size.
  • Added per-record ACK, a single retry, and a 3 s timeout so a dropped notification cannot hang the transfer.

7 · Records saving with no timestamp failure → fixed

21 September 2026 — before 18:48

  • Direct evidence: records 1–7 in the exported history read "Time not set".
  • Cause: the ESP32-C3 has no battery-backed RTC, so wall-clock time is lost at every power-off. Records were being written with ts = 0.
  • Fix: the web app now writes TIME:<unix epoch> to the control characteristic on every connect; the firmware validates it is after 1 Jan 2020 before calling settimeofday().
  • Records 8 onward carry real timestamps. The fix works.

5 · Technical write-up

5.1 · Objective

Build a low-cost, battery-powered device that measures ambient particulate concentration and fingertip cardiovascular signals at the same time, on the same timestamp, so that the two can later be examined together. The pairing is the point: PM exposure data and vitals data both exist separately and cheaply, but co-located and co-timed on one wearable unit they become a single record. This is an engineering prototype for demonstration, not a medical device, and nothing it outputs should be used clinically.

5.2 · Method

Particulate path. A Plantower PMS5003 draws air past a laser and counts scattering events, returning PM1.0, PM2.5 and PM10 in µg/m³ over a 9600 baud UART. It runs in passive mode: the firmware issues a read request every 5 seconds and abandons the attempt after 2.5 seconds so a lost frame cannot stall the main loop.

Cardiovascular path. A MAX30105 illuminates the fingertip with 660 nm red and 880 nm infrared LEDs and measures reflected light. Blood volume pulses modulate the reflected intensity. The firmware maintains a 100-sample rolling buffer at an effective 25 Hz (100 Hz sample rate, 4× hardware averaging) and processes it two ways in parallel:

  • Heart rate — 3-sample smoothing, then a 21-sample moving average subtracted to remove the DC baseline, leaving the AC pulsatile component. Peaks above 62 % of AC amplitude and spaced at least 25 × 60 / 160 samples apart are counted; BPM is derived from the mean peak interval. At least three peaks are required.
  • SpO₂ — Maxim's reference red/IR ratio algorithm, run only on windows that pass the quality gate.

Both outputs feed a 6-deep median filter with a 3-strike re-sync escape hatch, so brief noise is rejected but a genuine physiological change is not suppressed indefinitely.

Quality gating. A window is discarded if the IR channel saturates (> 220 000 counts), if AC swing is below 500 counts (finger resting too lightly), or above 8 000 counts (motion). Finger presence uses an adaptive baseline rather than a fixed threshold, followed by a 3 second settling delay.

Measurement protocol. The app writes START; the firmware averages every channel for 30 seconds, then appends one CSV record to LittleFS and notifies the app. Time comes from the phone — there is no RTC on board — via TIME:<unix> on each connect.

Interface. Live values appear on a 128 × 64 OLED and are notified over BLE at 1 Hz to a single-file Web Bluetooth client, which also pulls full history with per-record acknowledgement and renders a PDF report.

Breathing rate — what it actually is. The specification describes it as derived from PPG waveform analysis. It is not. The firmware computes RR = BPM/4 + (98 − SpO₂) × 0.5, clamped to 8–40 br/min. This encodes the textbook resting HR:RR ratio of roughly 4:1 and nudges it upward when saturation falls. It contains no independent information — it is a restatement of the heart rate and SpO₂ already displayed. Real PPG-derived respiration requires extracting respiratory sinus arrhythmia or the 0.15–0.4 Hz baseline wander from the PPG signal, neither of which this firmware does. Present this figure as a derived index, never as a measurement, or the write-up is dishonest.

5.4 · Limitations

  1. SpO₂ is the weakest link and the most likely thing to be challenged. A mean of 86 % on a healthy subject is a device fault, not a finding. Reflective PPG off a fingertip is intrinsically harder than transmissive, and the Maxim reference algorithm is uncalibrated. No result from this channel should be quoted as a saturation value.
  2. Breathing rate carries no independent information. See §5.2. It is a function of the other two outputs.
  3. 29 % of measurements captured nothing. The averager only accumulates when a pulse is being tracked, so a finger that shifts mid-window produces a zero record rather than a shortened one. This is a firmware design choice worth revisiting.
  4. No reference instrument, anywhere. Nothing here has been compared against a clinical pulse oximeter or a calibrated PM reference. Every "plausible" above means "internally consistent", not "accurate".
  5. n = 1. One subject, one indoor location, one two-hour window. No claim about population behaviour, exposure–response, or diurnal PM variation can be supported.
  6. PM sampling is co-located with the wearer's hand, not their breathing zone. The PMS5003 is in the same enclosure as the finger sensor, so what it measures is the air near the device, not inhaled air.
  7. No RTC. Timestamps depend on the phone connecting. A record saved before the app connects is written with ts = 0 and is time-orphaned — this already happened to 7 of 28 records.
  8. Battery life unverified, and the original 1000 mAh spec leaves no margin on the 4-hour target.
  9. GPIO9 as an OLED clock is a latent reliability risk — it is the boot strap pin. It has not caused a failure yet, which is not the same as being safe.

5.5 · What V2 should do first

  1. Borrow a clinical pulse oximeter and run 20 side-by-side measurements. Until that exists, the SpO₂ number is unpublishable.
  2. Either implement genuine respiratory extraction from the PPG baseline wander, or remove the breathing rate display entirely. Keeping a fake channel is worse than having no channel.
  3. Run the battery flat once, with a stopwatch, and write the number down.
  4. Move the OLED clock off GPIO9 to a free pin (GPIO2, 3, 4, 5 and 10 are all available).
  5. Save partial records with a validity count instead of discarding them as zeros.
